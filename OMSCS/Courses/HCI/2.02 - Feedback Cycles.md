## Gulf of Execution

- how do I know what I can do?
- how do I make these goals a reality?
- what actions do I need to take?
- what's the difference between what the user thinks they have to do, and what they actually have do do?
- steps in the gulf of execution
	- identify intentions
	- identify actions
	- execute the actions in the interface
- example issue: the user might know what actions they need to perform, but might not know how to trigger that action within the interface.
- the interface should cater to both novices and experts
- microwave example
	- User: "I need to heat this item for 1 minute"
	- Sensor: "I need to run the microwave until this item is 180 F"
- tips
	- make functions discoverable
	- let the user mess around
	- be consistent with other tools
	- know your user
	- feedforward
		- feedback on what the user might want to do
		- example: showing the refresh spinner as the user pulls down, but if the user aborts, the interface doesn't actually refresh

## Gulf of evaluation
- stages
	- interface output
	- interpretation
	- evaluation (were the goals achieved?)
- example: thermostat
	- I want this room hotter.
	- Press buttons on the thermostat.
	- Did I hear the furnace click on?
	- Is the room actually getting hotter?
	- Is the fan blowing?
	- sound and vent are not optimal feedback mechanisms
	- thermostat should indicate that it's running the HVAC system
- tips
	- give feedback constantly
	- give feedback immediately
	- match the feedback to the action
	- vary your feedback
		- visual
		- auditory
		- haptic
	- leverage direct manipulation
		- let the user feel like they're directly manipulating the system

## Reflection

I spent the better part of this past week setting up a Redis cluster in AWS, then trying to set up a Celery worker that used the Redis cluster as a broker and backend.

- How do I connect the worker to the cluster?
- How do I reframe my problem into the task abstractions Celery uses?
- How do I set up a Celery worker?

After building a prototype, this then followed with a pretty wide gulf of evaluation.

- Is the worker actually connected to the cluster?
- Can I find anything in Redis that indicates which queues/keys are being used by the Celery worker?
- Are there any obvious mechanisms that would allow external services to send tasks to this service worker?

In the end, it turns out that Celery doesn't support Redis clusters without using many workarounds, and only natively supports single-node Redis instances.

## Feedback Cycles

> When all else is equal, we want the system to stay consistent with the way users expect our systems to work.

In an electric car, why do we need to press the brake to turn on the car? Is this to prevent the car from rolling forward before the driver is ready to start moving?

The car can probably have some other mechanism for initiating the car's movement, such as starting the car in a "Neutral / Braked" mode, then having the driver select an initial "Forward" or "Reverse" action. This is in line with how ICE cars work (start in "Park", shift into "Drive" or "Reverse"), so it should match a drivers expectation on how to turn on a car. In this mode of operation, it doesn't matter if the driver holds the brake pedal when turning on the car.

Another suggestion.

> The car currently plays one sound when the power button is pressed, then plays a different sound if the car was successfully turned on. The button should play 1 of 2 different sounds when the power button is pressed. One should indicate that the car wasn't started. The other should indicate that the car was successfully started. That way the presence of a sound indicates that the button was pressed, and the NATURE of the sound indicates the outcome of the button press.
