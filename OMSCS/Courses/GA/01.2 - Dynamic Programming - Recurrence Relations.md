# 01 - Dynamic Programming - Recurrence Relations
There are 3 stages to designing an algorithm which leverages Dynamic Programming (DP).

## Defining a Subproblem
The first stage is to **define a subproblem**. Often this means taking a range of the problem of length $i$, where $1 \le i \lt n$, and then explicitly forcing the subproblem's solution to include the element at index $i$.

In practice, DP involves defining a specification for an in-memory "table" (1D, 2D, 3D, ...) of values. You place base-cases along the top/left periphery of the table. Then you incrementally populate the remaining values based on the ones you already have available, typically applying a min or max operation to the values you've seen so far. For the purposes of this "Subproblem Definition", the definition explains the meaning of each table entry in English.

## Defining the Recurrence Relation
The second stage is to **define a recurrence relation**, where you provide a mathematical definition of each table entry. Without a recurrence relation, a given algorithm does not exist within DP's solution space. Further, a recurrence relation is a mathematical specification, not a step-by-step algorithm.

Key characteristics of a recurrence relation:
- A recurrence relation is an equation.
- The equation provides a general rule for the recurrence.
- The rule defines the next term as a function of the previous term(s).

### Base Cases

Often the recursive definition depends on some base-case. Sometimes the base-case is built-in to the recurrence relation, like in [[6.1 - Contiguous Subsequence#Step 2 Define Recurrence Relation]]. Typically, the recursive definition is less clean, and the base case is specified as a separate equation.

1. Sometimes there are multiple base cases. Sometimes the base cases are defined as a range of values with bounds for the indices. If no indices are used (such as when there are only one or two individual base case table entries), bounds are not required. For example, $T[1] = 1$ does not have bounds because no variable is used.
2. The bounds for the indices in the base cases can be different and can be specified separately from the bounds for recurrence relation. Frequently, the bounds will be slightly different between the base cases and the recurrence relation.
3. The bounds as provided may/often convey directionality of how the DB table should be filled. For example, when the bounded range is $0 \le i \le n$, we assume a fill order of "left" to "right". If your approach depends on a right to left fill order (common for suffix-based approaches), then your bounds need to reflect this as well, e.g. $n \ge i \ge 0$.
4. Each unique table entry cannot be contradicted by setting it multiple times. In math, you cannot say $x=5$ and $x=3$ simultaneously. This should be reflected by comprehensive and mutually-exclusive conditions where `otherwise` can be used to specify "all other conditions".
5. Similarly, a table entry defined mathematically can only have one value. For example, if $L(0,7)$ is defined under the base cases, $L(1, 5)$ would be defined by one of the two options in the recurrence relation. It is ok for the exact same table entry to be specified more than once in a recurrence relation, as long as it is set equal to the same value across all instances.
6. Table entries cannot be overwritten. While this would be acceptable in pseudocode where there is a sense of "before", "after", and "iterations", these concepts are not present in a mathematical definition. A table entry is not a temporary variable to store data in this context; it is a clearly, mathematically defined value. This point is similar to the previous bullet.
7. All table entries that are used to generate the value of any other table entry have a clearly defined value. In other words, there is no scenario where an undefined table entry is used to calculate the value of another table entry.
## Implementation Analysis
Implementation analysis is an important stage, because it helps identify possible flaws with the given approach.

1. State the number of subproblems in big-O notation. For DP, this is effectively the size of the in-memory table being used.
2. State the runtime required to fill the table.
3. State how/where the final return is extracted from the table. Sometimes it's a sum, a max, the last entry, etc. This depends on the problem and recursive definition.
4. State the runtimes required to extract the final return in big-O notation.

## Examples
### Example 1 - One Variable Multiple Definitions 
#### Bad
- **Base Case:** $T[i] = 0 : 0 \le i \le n$
- **Recurrence:** $T[i] = T[i-1]+1 : 1 \le i \le n$

Note that in range $1 \le i \le n$, $T[i]$ is defined twice, with differing values. The intent was that $T$ should be initialized to $T=\{0, \space ..., \space 0\}$, where $|T|=n+1$. That is fine for the pseudocode, but not fine for the mathematical definition.
#### Good
- **Base Case:** $T[i] = 0$
- **Recurrence:** $T[i] = T[i-1]+1 : 1 \le i \le n$

### Example 2 - Infinite Loop
#### Bad
- **Base Case:** $T[i] = 0$
- **Recurrence:** $T[i] = \max \{ T[i], \space T[i-1]+1 : 1 \le i \le n \}$

In this case, we're using the undefined $T[i]$ to define $T[i]$. Again, this is fine in pseudocode (as long as the $T$ array is property initialized), but not fine in mathematical definition.

To fix this, you can add helper indices if needed to access a range of previous table entries, as long as the helper indices are clearly defined and bounded.
#### Good
- **Base Case:** $T[i] = 0$
- **Recurrence:** $T[i] = \max \{ T[i-1]+1 \space : \space 1 \le i \le n \text{ and } 0 \le j \lt i \}$
