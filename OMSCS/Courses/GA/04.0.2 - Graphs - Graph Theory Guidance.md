# 04.0.2 - Graphs - Graph Theory Guidance
Below contains the content of a post on the course forums on how to approach Graph Theory problems in this course.

## Context
A graph theory problem is a form of **reduction**. You are given some problem to solve, and the challenge is to solve that problem by using one of the graph algorithms that we study during the semester. In other words, take a given problem statement, and then **reduce** the problem statement to a graph problem such that a known graph algorithm can solve it.

The **known algorithms** are treated as a black box. These algorithms are enumerated in [[04.0.1 - Graphs - Black Box Algorithms]]. You can/will modify the original problem input in some way or create a graph which represents the input. This becomes the input to the black-box algorithm. You then use the outputs from the black-box, plus any necessary modification, to output a solution to the original problem.

## Rules
- Like the Divide and Conquer lessons, pseudocode is absolutely not allowed in any form. Extrapolated mathematical definitions are considered pseudocode.
- We may **only use known and permitted** black-box algorithms from [[04.0.1 - Graphs - Black Box Algorithms]].
- You **must use one or more** black-box algorithm to solve problems.
- You **must not modify** any black-box algorithm. Recreating the algorithm with modifications is the same thing as modifying the existing implementation.
- All graphs are given in adjacency-list format.
	- You can assume that you always have $n$ and $m$ for purposes of runtime analysis. $n=|V|$. $m=|E|$.
	- See [[00.7 - Common Course Runtimes]] for relevant big-O runtimes for dealing with Graphs expressed as adjacency lists.

## Required Parts of a Graph Theory Solution
### Algorithm
- Describe "how" to solve the problem in words (narrative form)
	- Bulleted steps are fine, but pseudocode/code is not allowed.
	- Precise mathematical definitions and redeclarations are considered code.
	- "Pseudocode" includes line-by-line restatement of code as words.
	- If you find yourself using a lot of nested bullets, you might be erring on the side of line-by-line conversion of code into words, which is not a narrative.
- Describe what **modifications are performed to the input**, if any are required
- Detail the black-box algorithm(s) being used.
	- What is passed in as input?
	- What is being used from its output?
- Describe what **modifications are performed to the output**, if any.
- Repeat as needed for any other black boxes.
- Detail the final return for the problem's solution.

### Justification of Correctness
- Describe "why" the algorithm solves the problem, in words (narrative). This is not a formal inductive proof. Informal justification is okay. In fact, we'll find that there's not nearly enough time in this semester for formal proofs.
- Explain how your problem is solved by the black boxes used.
- Explain how changing the inputs and/or outputs gets what you want.

### Runtime Analysis
- Analyze **all** steps of the algorithm in **Big-O Notation**
	- As always, this course deals in worst-case Big-O
	- Can explain/analyze in words and assert known black-box runtimes without further justification.
	- Must include runtime analysis for any pre/post processing.
	- See: [[00.7 - Common Course Runtimes]]
- Provide an overall final runtime in Big-O notation, fully simplified.
- If the problem specifies a target runtime, you must meet that runtime for full credit. If a target runtime is not specified, faster/correct algorithms receive more credit than sub-optimal solutions.
- While we work with worst-case runtimes, we also work with *tightest-bound* runtimes.
	- Even though the worst case for an $O(n+m)$ operation occurs when $m=n^2$, it is incorrect to state $O(n^2)$ unless we know something about the topology of the graph. Otherwise, $O(n+m)$ is the tightest worst-case bound on such an operation.
	- If we know that the graph is a tree, then $m=n-1$ and therefore $O(n+m)$ operations collapse to $O(n)$. It also collapses to $O(m)$, but it's preferred to use $O(|V|)$ over $O(|E|)$ when possible. Don't intentionally confuse the TAs. They're overworked and underpaid.
- When conveying the well-known runtimes of usable black boxes, you are not required to simplify it, even if the graph's constraints would allow for it.

## Graph Representation
Graphs in this course **unless stated otherwise**...

- Are always "simple graphs". No multi-edges. No self-loops.
- Are always given in adjacency list format.
	- An array of vertices that are pointers to to linked lists of adjacent vertices, such that each element in the list represents an edge to another vertex
	- Vertices are assumed to be labeled in such a way where they can be found by indexing into the array.
- Can be connected or disconnected, undirected or directed, sparse or dense
	- If unstated by the problem, you should assume any of these could be true.
	- Are connected and undirected when working with MSTs
	- Are connected and directed when working with flow networks

When working with graphs, there are a number of common actions that can be presented without needing to go into details. Some examples as follows:

- Reversing a graph
	- "Reverse the edges in the graph"
- Copying a graph:
	- "Create a copy of G and call it GCopy"
- Creating subgraphs:
	- "Create a copy of G called GEven that only keeps edges with even numbered weights"
	- "Create a copy of G called GK that only keeps vertices with a degree > k"
	- "Create a residual graph of G called Gre that uses the flows from our run of EK"

Unless the task can't possibly be completed in this runtime, each of these operations are assumed to be $O(n+m)$ operations.
